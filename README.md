# WorkForCigarmonica
This repository contains both the initial version of the dialogue system I made for Cigarmonica and the second version that if my memory is right, was used for the shipped version. Bear in mind that I was inexperienced when writing this code; I am working on a portfolio entry describing how I'd change it now. I make no guarantees for code quality or professionalism of comments that I wrote at this time. I hope they're professional, but... its entirely possible there could be a curse word or too if a comment is related to a bug.

Cigarmonica is game made for a game jam that was conducted during the spring of my freshman year of college by my college's Game Design Club. Our goal was to build a small game, all together, as a club. While in total there were roughly 10 people participating, I wound up only one of two (originally three) programmers. This was my first experience with developing video games in a team, and my first time ever helping to release a game on Itch.io (or anywhere, for that matter). This project helped me to learn a lot about the Unity Engine, and about programming complex systems which non-technical developers should in theory be able to use.
The game is about a man who has been arrested and has five days until he is to be executed. The player must try and trade items around the prison for other items, in order to exchange their way to freedom. 

In short for what changes I'd make, though:
- movement would use a navmesh rather than changing the location
- Interaction would largely remain generally the same, though actions would probably have an input queue of sorts to ensure the player could walk somewhere and then interact as I think my previous solution was kind of hacky or hard coded if my memory is right
- There would be an indicator when the cursor is over something that can be interacted with
- Camera positions would be planned more effectively
- Dialogue system would be planned period.
-   I'd store each conversation as a graph for sure rather than as a list of strings
-   Each line of dialogue would also contain who says it. Can't believe I forgot to think about that. 
-   I'd probably be using a blackboard to handle getting all the conversations or the conversation to play
-   I'd probably use handles for identifying and storing dialogue lines, dialogue conversations, any conditions or tags that have to be stored, maybe in a SQLite database or just a good old binary search tree (if my theory that a handle can just be a number is right) or something. I still don't fully understand handles, admittedly, but I think it'd be hard to get a working product that is also worse than this. I believe I could use handles to make editing and changing data easier for specific dialogue. 
-   memory would be spread between what I'm going to call "working, short term, and long term" storage, for characters and for the game itself --- working is just constrained to the conversation, and probably just means that the conversation branches depending on the player's choices. Short term is for something that will matter after the conversation ends, but may not affect the actual levels that come after. Long term would be like major decision (though this game wouldn't have had those) that need to persist beyond the level
-   Broadly speaking, I'd better adhere to separation of concerns and composition rather than inheritance. The system for "commands" would probably be separate from whatever displays dialogue (which would be separate from what actually "reads" the dialogue and controls it all). I'd make ample use of events and delegates and probably a messaging system too to connect the actual "commands" to what actually executes them (and that would probably involve some kind of stack).
